# 面试讲解稿

> 原则:先讲结论和证据,主动交代局限。所有数字都能在仓库里查到出处(见末尾速查表)。

## 30 秒版

我在字节开源的 Agent 框架 DeerFlow 上做了可靠性评测与修复。它的文献综述 Agent 会**整篇编造论文**:30 个主题里 4/29 份报告有一半以上引用是虚构的。我逐个追踪调用链,发现根因是检索输出过长被框架换成摘要,Agent 没读回原文就开始补全。我没有去调提示词,而是让论文数据由脚本落盘、模型不再转述,并在报告写完后用代码核对每个 arXiv 编号。在 10 个没见过的主题上,三项约束(引用真实、时间窗口、类别)全满足的运行从 1/10 提到 10/10;代价是 token 多了 21%。

## 2 分钟版(按 背景 → 问题 → 根因 → 方案 → 结果 → 局限)

1. **背景**:想做一个能写进简历的 Agent 项目,选了 DeerFlow(MIT,有子 Agent / 沙箱 / skills / 中间件)。重点放在**评测与可靠性**,因为做功能的人多、做评测的少,而且结果可量化。
2. **先量化**:30 个主题 × 1 次,用 arXiv 官方 API 逐条核对。主指标是"已验证"(编号存在**且标题对得上**)。基线:引用已验证 86.9%,4/29 严重编造,时间窗口和类别各只满足约 70%。
3. **查根因**:逐个追踪工具调用链。检索输出约 19,600 字符,超过 12,000 的外置阈值,Agent 只看到一份摘要(结构说明 + 首尾片段,中间的论文看不到)。摘要里其实写了"用 read_file 读回原文",**框架提醒了,模型没照做**。**读回原文的 18 个运行 0 个编造;没读回的 4 个运行 4 个全部编造**。
4. **方案**:不靠提示词叮嘱,而是**让模型没有机会转述数据**:脚本做检索与过滤、结果落盘分批、子 Agent 读文件、报告后 `verify`。以 custom skill 同名覆盖,不动核心。
5. **迭代**:v2.0 消除了编造,却让 7/30 的报告凑不够 10 篇(精确短语太窄,Agent 还自己去掉类别过滤来凑数)。v2.1 由代码放宽查询、锁死用户约束。
6. **验证**:因为 v2.1 是看过失败后写的,30 主题成绩是样本内;所以**运行前**写好方案(`eval/HOLDOUT.md`),在 10 个未见主题上对照:**1/10 → 10/10**。
7. **局限(主动说)**:样本小、编造次数差异不显著、成本没降、不评价综述内容质量。

## 简历写法

可以写:
- 搭建 30 + 10 主题的文献综述评测,以 arXiv 官方 API 逐条核对引用(已验证 / 第一作者 / 时间窗口 / 类别)。
- 逐个追踪调用链定位到根因:工具输出被外置后未读回 → 整篇论文被编造(读回 0/18,未读回 4/4);以确定性代码(落盘分批 + 编号核查)替代提示词约束,不改框架核心。
- 在 10 个未见主题上,引用真实、时间窗口、类别三项全满足的运行 1/10 → 10/10。

**不要写**:"编造率从 14% 降到 0%"(不显著)、"成本降低"(实测 +21%)、"成功率提升 X%"(没有定义过这个指标)。

## 常见追问

**为什么不直接改提示词?**
提示词只能让模型"更可能"去读文件,而这是个概率事件;4/4 的编造运行恰恰是没读。把论文数据从模型手里拿走,这条路径就不存在了。我也没把核查关卡当成可靠的:冒烟时就见过 Agent 没按要求运行 `verify`,所以关键保证放在"模型根本不转述数据"上,`verify` 是第二道防线。

**怎么证明因果?**
证明不了,我也没这样说。这是对 29 个运行逐个追踪得到的观察性分组(18 对 4,p = 0.00014),加上对单个运行的完整调用链复盘(t01:摘要只有首尾片段,10 篇里只有 1 篇是真的,其余编号/标题/作者全是编的,甚至写成 "Various authors")。留出集基线臂里可追溯的 2 个严重编造也落在同一机制上。

**你的评测指标会不会自欺?**
会,而且遇到过。最早的 `resolved`(编号存在)被虚构编号蒙混过关:一份实际只有 1/10 真实的报告得了 10/10。因为虚构编号恰好对应别的真实论文。所以改成 `verified`(编号存在**且标题匹配**)。另外"外置导致编造"这个说法我也先下后撤、再用全量追踪修正过,过程都留在 BASELINE.md 里。

**为什么 token 反而高了?**
没做消融,只能推测:v2.1 流程更完整(落盘、分批、核查),且基线臂有 1 个运行早早失败拉低了均值。我没把成本当成卖点。如果要降,可以让子 Agent 用更便宜的模型,但那需要重新评测。

**10 个主题够吗?**
对检验"编造率"不够(基线 14%,10 个只期望 1~2 个事件),我在方案里写明了这一点,没有拿它做显著性声明。对约束遵守这类基线差距很大的指标够用(1/10 对 10/10,p = 0.0001)。

**留出集怎么保证没作弊?**
主题和指标在运行前提交到仓库(提交记录可查),运行期间不改 skill,两臂同一晚连续运行。基线臂有 1 个运行原因不明地中断,按事先写好的规则(只有额度拒绝才排除)计为失败,排除它结论也不变。

**遇到的最大的坑?**
LocalSandbox 只翻译命令行里出现的 `/mnt/user-data/...`。脚本内部默认的输出路径会落到容器字面路径上,文件工具和子 Agent 都看不到,结果 Agent 绕了一大圈,最后只交出 3 篇。修法是让 `--out-dir` 必填,路径必须出现在命令行。

**DeerFlow 的架构怎么讲?**
Nginx 统一入口,Gateway(FastAPI,内嵌 LangGraph 运行时)+ Next.js 前端。主 Agent 靠约 50 个中间件塑形(上下文注入、skill 激活、摘要压缩、循环检测、token 预算等),用 `task` 工具派发子 Agent(并发上限 3,不能再嵌套派发)。skill 是以 `SKILL.md` 为单位的工作流说明。我的改动只落在 skill 层:custom skill 按同名遮蔽 public skill,所以前后对比用的是完全相同的 prompt。

**这个方案的通用性?**
思路是通用的:凡是"模型要把工具返回的结构化数据原样搬运给下游"的地方,都应当用文件和代码搬运,并在出口做一致性核对。这个仓库只在 arXiv 文献综述上验证过,没有更多场景的证据。

**如果再有时间?**
(1) 每个主题重复 ≥ 3 次,给出置信区间;(2) 评价综述内容本身的质量(现在只核对引用);(3) 降成本;(4) 把外置未读回这一类问题整理成上游 issue。
